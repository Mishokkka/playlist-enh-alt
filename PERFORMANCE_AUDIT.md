# Аудит Playlist Enchantment для Foundry VTT 13

Дата: 2 ноября 2026 года. Установлена локальная сборка **1.3.11**.

Последующая проверка PR №1 добавила исправления группового переключения, паузы на нуле, отменённых загрузок и скрытого popup, а также линейное сопоставление переходов. Подробности и актуальные результаты — в [PR_REVIEW.md](PR_REVIEW.md). Приведённые ниже 92 проверки относятся к этапу 1.3.10.

После первого аудита проведено повторное ревью: в 1.3.9 воспроизведены и исправлены ошибки совместимости и жизненного цикла. Подробности, регрессии и ограничения проверки описаны в [REVIEW.md](REVIEW.md); его выводы уточняют первоначальные результаты.

Исходная локальная версия: 1.3.8 с предыдущими пользовательскими исправлениями. Проверенный движок: **Foundry 13.351**, исходники из `D:/Foundry/v13/Foundry Virtual Tabletop/resources/app`.

## Что изменилось между ветками upstream

Сравнение выполнено по исходникам и истории коммитов, а не только по описанию релиза.

Первый переход на v14 (1.4.0) добавил числовую обработку длительности fade и правильное хранилище Forge. Затем появились автоматическая музыка боя, разделение аудиоканалов и исправления обычного переключения плейлистов. В сентябре модуль превратился в существенно более крупный проигрыватель: отдельное окно Studio, обложки, теги, очередь, DJ-доступ, soundboard/ducking и новый процесс загрузки файлов.

В v14 также изменился формат контекстных меню: вместо `name` / HTML-иконки / `callback` используются `label` / классы иконки / `onClick`. Поэтому файлы новой ветки нельзя просто положить поверх версии для v13. Сама версия 2.0.3 не означает устранения всех старых проблем производительности: в её боковой панели остаются повторное навешивание обработчиков после частичного рендера и полная перерисовка панели после изменения громкости в popup.

Полный Studio с очередью и DJ-доступом требует отдельного переноса интерфейса, настроек и серверных запросов. Для этой сборки перенесены совместимые исправления существующего проигрывателя и устранены найденные источники нагрузки.

Источники: [ветка v13](https://github.com/Plushtoast/playlistenchantment/tree/3dd26156809a8ebdd6acd682fba40873605eb0a6), [ветка v14](https://github.com/Plushtoast/playlistenchantment/tree/a91d2978f22dd33ccdf7c7b9f75e46e899d14124), [первый переход на v14](https://github.com/Plushtoast/playlistenchantment/commit/4f7d70c122884bf96b745b8c65ebe2450eb9bc9a), [исправления S3](https://github.com/Plushtoast/playlistenchantment/pull/16), [API PlaylistDirectory v13](https://foundryvtt.com/api/v13/classes/foundry.applications.sidebar.tabs.PlaylistDirectory.html).

## Главная находка в аудиокоде v13

В установленном Foundry 13.351 `PlaylistSound._scheduleFadeOut()` вызывает `Sound.schedule()`, а тот создаёт `AudioTimeout`. Его реализация выделяет пустой `AudioBuffer` на **всю длительность ожидания**. Это происходит даже при нулевом fade.

Для задержки 300 секунд при 48 кГц получается:

`300 × 48 000 × 4 = 57 600 000 байт ≈ 54,9 МиБ`

Это отдельный буфер таймера, дополнительно к декодированной музыке. Несколько дорожек и повторные запуски увеличивают объём выделений. Такое поведение — конкретный кандидат на скачки памяти и статтеры при начале воспроизведения; причинную связь с FPS вашего мира пока не удалось измерить.

Модуль регистрирует подкласс `PlaylistSound` через стандартный `CONFIG.PlaylistSound.documentClass`. Он заменяет только планирование штатного fade в конце трека:

- при нулевом fade таймер не нужен;
- для положительного fade используется беззвучный `ConstantSourceNode`, не подключённый к выходу;
- начало fade привязано к часам соответствующего `AudioContext`, включая приостановку и возобновление контекста;
- учитываются оставшееся время после паузы и штатное ограничение fade половиной трека;
- пауза, остановка, конец трека и удаление документа очищают таймер;
- `_cancelFadeOut()` остаётся доступным другим аудиомодулям;
- при неподдерживаемом контексте используется штатный механизм; чужая реализация планировщика сохраняется.

В настройках модуля появился клиентский переключатель **Optimize fade timers**, включённый по умолчанию. Для сравнения поведения его можно выключить и перезагрузить клиент. Основа механизма описана в [спецификации Web Audio](https://www.w3.org/TR/webaudio-1.1/#ConstantSourceNode).

Реализация находится в `modules/audio-scheduler.js`. Проверенные исходные места движка: `client/documents/playlist-sound.mjs`, `client/audio/sound.mjs`, `client/audio/timeout.mjs`.

В соседней установленной папке The Sound of Silence найдено дополнительное использование `Sound.schedule()`. Если этот модуль активен, его собственные таймеры тоже могут выделять длинные буферы. Оптимизация здесь относится к штатному таймеру `PlaylistSound`; отдельные таймеры других модулей требуют собственного профиля. Вызовы `_cancelFadeOut()`, которыми The Sound of Silence отменяет штатный fade, поддерживаются.

## Остальные исправления производительности

| Проблема | Исправление |
| --- | --- |
| Popup присваивал `range-picker.value` при обновлении интерфейса. В v13 этот setter генерирует `input` и `change` и округляет значение | Тихое обновление представления без записи громкости, fade и синтетических событий |
| Каждый тик повторял поиск строк и вложенных элементов | Ссылки на элементы кешируются при рендере; далее выполняется один проход по строкам |
| Один и тот же текст времени записывался заново | Текст обновляется только при изменении |
| Таймер продолжал обрабатывать скрытые поверхности | В скрытой вкладке обработка пропускается; боковая панель и её отдельное окно проверяются на видимость |
| Изменение громкости popup запускало рендер панели | Громкость синхронизируется на месте; штатная задержка записи в БД сохраняется |
| На каждую строку назначались отдельные обработчики | Три делегированных обработчика на контейнер, независимо от размера библиотеки |
| Возобновление N дорожек вызывало N обновлений плейлиста | Полный одновременный набор возобновляется одним штатным `playAll()`; частичный — через `playSound()`, сохраняя обработчики других модулей. Играющие дорожки не перезапускаются |
| Popup использовал `_playing`, являющийся кешем рендера | Состав берётся из живых документов по событиям; таймер работает только с уже показанными строками |
| Несколько событий могли выстроить очередь рендеров | Обновления объединяются, изменения во время рендера применяются после его завершения |
| Быстрые наведения могли создать конкурирующие popup | Создание сериализовано, устаревшие запросы отбрасываются, таймеры закрытия очищаются |

## Совместимые исправления поведения

- Восстановлен `data-sound-uuid`, который ожидает штатный код v13.
- Crossfade использует штатное воспроизведение и затухание документов v13 на каждом клиенте. Дополнительные локальные рампы, ожидание загрузки на 50 мс и отложенные `stopAll()` удалены.
- Обрабатываются все активные дорожки одновременного плейлиста. Быстрые переключения и последующая ручная остановка не оставляют старых команд остановки.
- Перенесена логика переключения в пределах аудиоканала. Новая музыка в `music` сохраняет слои, назначенные `environment` или `interface`, и soundboard. Дорожки, оставленные в `music`, относятся к тому же музыкальному каналу.
- При включённом Fade обычный запуск и запуск из сцены останавливают другие плейлисты этого канала. Повторные события родительского и дочернего документов объединяются. Команда возобновления всех плейлистов допускает совместное воспроизведение.
- Нормализация применяется ко всем запускаемым дорожкам и сохраняет настоящий ноль. Некорректные значения длительности не передаются аудиодвижку.
- Штатный Stop All очищает оставшиеся позиции паузы; Pause All сохраняет их.
- Кнопка Play в popup запускает назначенный ему макрос, даже если уже играет другой плейлист.
- Загрузка учитывает Forge и S3 bucket/key, сохраняет выбранный S3 bucket, повторно использует существующие файлы и проверяет ответ сервера. Неудачный файл не создаёт ложной записи или пустого плейлиста; остальные файлы обрабатываются.
- Анимация длинных названий ограничена интерфейсом модуля и учитывает системное предпочтение уменьшенного движения.

Явный crossfade передаёт разовую длительность в параметрах штатной операции обновления. Сохранённые поля fade не меняются, а затухание в конце трека использует прежнее значение. Исключение — намеренное обновление значения плейлиста включённой пользователем глобальной настройкой always-Fade. Воспроизведение и остановка проходят через публичные методы Foundry, сохраняя обёртки других модулей.

## Проверка

**92 автоматические проверки:** 31 проверка интерфейса/управления/загрузок, 16 проверок аудиопланировщика, 18 проверок расположений файлов, 12 регрессий 1.3.9 и 15 проверок полного клиентского жизненного цикла. Все 12 новых регрессий падают на сохранённой 1.3.9 и проходят на 1.3.10.

Тесты загружают реальные классы из установленного Foundry 13.351: `Playlist`, `PlaylistSound`, `Sound`, `PlaylistDirectory`, `AudioHelper`, `HTMLRangePickerElement`, `AudioTimeout` и `EventEmitterMixin`. Для жизненного цикла используются полные тела классов Sound/PlaylistSound/Playlist, включая приватные поля. Базовая модель данных, DOM, хранение, транспорт и аудиоустройства заменены управляемыми тестовыми объектами. Исходники Foundry не включены в модуль.

Проверено, в частности:

- настоящий setter v13 генерирует два события, а обновление popup — ноль;
- 1000 строк × 30 неизменившихся тиков после построения кеша дают **0 запросов селекторов и 0 перезаписей текста**;
- полный набор из 100 одновременных дорожек возобновляется одним штатным запросом;
- запуск и остановка вызывают публичные `playAll()` / `playSound()` / `stopAll()` / `stopSound()`, включая обёртки;
- сериализованные параметры разового fade применяются на двух моделях клиентов без записи в сохранённые поля;
- загрузка с задержкой, повторный запуск во время затухания и запоздалые события старого файла не нарушают состояние текущего источника;
- исходный `AudioTimeout` запрашивает 57 600 000 байт для пяти минут; тест считает размер без фактического выделения этого большого буфера;
- новый планировщик не вызывает `Sound.schedule()` и корректно отменяет устаревшие события;
- шаблон компилируется настоящим Handlebars из установки Foundry;
- стартовый файл модуля регистрирует настройки и классы.

Повторный запуск из папки модуля, Node.js 24:

```powershell
node --test --test-isolation=none tests/performance.test.mjs
node --test --test-isolation=none tests/audio-scheduler.test.mjs
node --test --test-isolation=none tests/filelocation.test.mjs
node --test --test-isolation=none tests/review-regressions.test.mjs
node --test --test-isolation=none tests/native-lifecycle.test.mjs
```

Для другого пути установки задайте переменную `FOUNDRY_V13_APP`, указывающую на `resources/app`. Раздельный запуск тестовых файлов нужен для изоляции тестовых глобальных объектов. В текущем окружении создание дочерних процессов обычным `node --test` ограничено, поэтому используется `--test-isolation=none`.

Доступ к окну Foundry был отклонён инструментом управления приложениями; отдельный браузерный прогон Web Audio также заблокирован политикой разрешённых URL. Поэтому **FPS живого мира, фактический расход памяти браузера и прослушивание переходов ещё не измерены**. Прохождение тестов подтверждает проверенные операции и расчёты, но не гарантирует устранения всех статтеров.

## Применение и проверка в игре

Файлы уже обновлены в папке модуля. Перезапустите Foundry и перезагрузите страницу у каждого клиента, чтобы загрузился новый JavaScript. В списке модулей должна отображаться версия 1.3.11.

Проверьте один длинный трек, одновременное воспроизведение, Pause/Resume, быстрые переключения макросов и окончание трека. Затем сравните движение карты при скрытой и открытой панели плейлистов и при открытом popup.

Для ограниченного замера подготовлен дополнительный модуль, который запускается вручную в консоли браузера:

```javascript
const { profilePlayback } = await import(foundry.utils.getRoute("modules/playlistenchantment/tools/profile-playback.js"));
await profilePlayback(20);
```

Он за 20 секунд собирает интервалы кадров, длинные задачи (если поддерживаются браузером) и число рендеров/обновлений документов. Сравнивайте одну сцену и одинаковое движение карты при остановленной музыке и при воспроизведении. Для проверки аудиопланировщика можно повторить замер с выключенным Optimize fade timers после перезагрузки. `tabWasHidden: true` делает сравнение кадров ненадёжным. Результат остаётся в консоли; профайлер не запускает и не останавливает музыку и не меняет документы.
